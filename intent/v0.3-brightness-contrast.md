# v0.3 Brightness and contrast

## Goal

The second edit entry becomes active. The user adjusts brightness, contrast or colour
temperature with one slider, optionally drops all colour, sees the result immediately, and
bakes it into the image on confirm.

## Scope

In:
- Brightness/contrast view with the frame region of the image, one slider, segmented
  [brightness|contrast|temperature], a grayscale toggle, [back], [confirm].
- Live preview through CSS `filter: brightness() contrast() url(#temperature) grayscale()` on the
  displayed canvas (no pixel work while dragging); the temperature step is an inline SVG
  `feColorMatrix` in sRGB.
- Colour temperature (added 2026-09-22): a red/blue channel gain, cool .. warm, so a colour cast
  that contrast edits bring out on white paper can be neutralised.
- Grayscale toggle (added 2026-09-22): drops all colour with the CSS `grayscale(1)` luminance
  weights. It is a toggle, not a one-way action, so it can be switched off again before confirm.
- Confirm applies the same filter through the 2D canvas `filter` property (Chrome, Safari 16.4+) and replaces `capture.image`.
  Fallback: manual per-pixel loop with the same formula if `ctx.filter` is unsupported.
- Back discards the pending values.

Out: gamma, black-and-white threshold, auto-levels.

## Behaviour

- Ranges: brightness 0.5 .. 1.5 (neutral 1.0), contrast 0.5 .. 2.0 (neutral 1.0), temperature -1 .. 1
  (neutral 0; at the ends red and blue move by 20 % in opposite directions). The slider is linear in the
  displayed range with a tick at neutral. Switching the segment swaps which value the slider shows.
- Filter order: brightness, contrast, temperature, grayscale.
- The view shows the frame region only, like the captured view, since the margins are not relevant here.
- Slider is a native `<input type="range">` styled icon-only; label via `aria-label` only.
- Confirm: draw `capture.image` onto a new canvas with `ctx.filter = "brightness(b) contrast(c) grayscale(1)"`,
  replace the image. A non-neutral temperature needs an SVG filter reference, which canvas contexts do not
  support everywhere, so the whole chain then goes through the pixel loop. The frame is unchanged. All
  values then reset to neutral for the next visit; edits accumulate in the image.
- Baking affects the whole captured image including margins so that later cropping stays consistent.

## Icons used

`brightness`, `contrast`, `temperature`, `grayscale`, `arrow-left`, `check`.

## Implementation notes (2026-09-22)

- `src/tone.ts` holds the ranges, the CSS filter string, the temperature colour matrix and the
  per-pixel formula from the Filter Effects spec (brightness: slope b; contrast: slope c, intercept
  0.5 (1 - c); temperature: per-channel gain; grayscale: sRGB luminance 0.2126 / 0.7152 / 0.0722;
  each step clamped), plus the lookup-table pixel loop used as fallback. `bakeTone` in `src/bake.ts`
  checks for `filter` on the 2D context prototype and otherwise processes the image in
  256-row strips so only one strip of `ImageData` is held at a time.
- The slider is a native range input with `min`/`max`/`step` set from the selected value's
  range; the neutral tick and the filled part of the track are CSS variables set from JS,
  because native `datalist` ticks render inconsistently on mobile.
- Rounding at exact half levels may differ by one between the canvas filter and the fallback
  loop, as it does between browsers; the unit test allows that tolerance.

## Acceptance criteria

- Dragging the slider updates the preview within one frame on a mid-range Android phone (no canvas redraw per event).
- Confirm output matches the preview visually; unit test verifies the fallback loop against the filter formula on a small image.
- Neutral values leave the image bit-identical.
- Back leaves the image unchanged.
