# v0.5 Multi-page PDFs

## Goal

A scan can consist of several pages. The captured view gets a fourth button [+] that opens
the camera for the next page; with more than one page a header shows the position ("2/2")
and arrows to move between pages. Share builds one PDF with all pages in order. Pages are
never reordered; the capture order is the page order.

## Scope

In:
- Button bar on the captured view becomes [back] [share] [edit] [+].
- [+] opens the camera; the new capture is appended after the last page and becomes the
  current page. Camera back (button or hardware) returns to the captured view of the page
  that was current before, without adding anything.
- Page header (only with two or more pages): [previous] "n/m" [next], centred above the
  image. The arrow at an end is disabled. "n/m" is the second text exception after
  Klein / Mittel / Groß (decision 2026-09-22): a number is language-neutral and there is no
  icon that says "page 2 of 3".
- Back on the captured view: with several pages it removes the current page and shows the
  previous one (the next one if the first page was removed). With a single page it behaves
  as before: discard and reopen the camera. No separate delete button (decision 2026-09-22).
- Edit views (crop/rotate, brightness/contrast) work on the current page only; confirm bakes
  into that page's image as today.
- Share: the sheet is unchanged; confirm renders every page's frame region at the chosen
  quality and builds one PDF with one A4 page per scan, each page's orientation following its
  own crop. Success discards all pages and returns to the start page; cancel keeps all pages
  and the current position.
- Memory: only the current page holds a full-resolution canvas. Pages that are not on screen
  are parked as a full-image JPEG blob plus their frame (decision 2026-09-22, see Behaviour).
- Soft limit of 20 pages: [+] is disabled at the limit. Blobs of about 3 to 6 MB each keep
  twenty pages well under 150 MB, which a mobile tab can hold; canvases could not.
- History integration (v0.4) extends to the page navigation: switching pages does not push
  a history entry (it is not a screen change); [+] pushes the camera entry as today.
- Swiping horizontally over the image moves between pages as the arrows do: swipe left for
  the next page, right for the previous one. A swipe at an end does nothing.

Out: reordering, page thumbnails, deleting a page other than the current one, mixing scans
from different sessions, persisting pages across a reload (no retention, as always).

## Behaviour

Document and pages
- The app holds a `Document` (`pages: Page[]`, `current: number`) instead of a single
  `Capture`. A page is `{ image: HTMLCanvasElement | null, blob: Blob | null, width, height,
  frame: Frame, dirty: boolean }`. Exactly the current page has `image` set; every other page
  has `blob` set. `width`/`height` are the full image size in pixels, needed for the frame
  maths while the page is parked.
- Parking (leaving a page via [+], previous, next or back-removal of another page): if the
  page is `dirty` or has no blob yet, the full image (not just the frame region) is encoded as
  JPEG at quality 0.95 with `canvas.toBlob`, the blob stored, `dirty` cleared and the canvas
  released. A page whose image has not changed since it was parked last time keeps its blob
  untouched, so navigating back and forth causes no repeated generation loss. Only a bake
  (rotation, tone) sets `dirty`; cropping does not, it only updates `frame`.
- Waking (a page becomes current): the blob is decoded with `createImageBitmap` (fallback:
  `Image` with an object URL) into a fresh canvas of `width` x `height`; the blob is kept.
- Both parking and waking are asynchronous and run behind the busy overlay (v0.4 rules), so
  a page switch shows the spinner for the few hundred milliseconds a 16 MP JPEG takes.
- The capture of a new page follows the existing capture path; it becomes a page with
  `image` set, `blob` null, `dirty` false (nothing to re-encode until it is parked).

Captured view
- Shows the current page's frame region as today. The header is rendered only when
  `pages.length > 1`; it carries `aria-label`s "Vorherige Seite", "Nächste Seite" and the
  position text with `aria-live="polite"`.
- [+]: `aria-label` "Weitere Seite scannen". Disabled at the page limit.
- Swipe: a pointer drag over the stage of at least 48 px whose horizontal part clearly
  dominates the vertical one (twice as long) counts as a swipe; shorter or steeper drags are
  ignored, so vertical scrolling gestures and taps do nothing. Only with two or more pages,
  never while busy or while the popover or sheet is open.
- Back with several pages: remove the current page (release its canvas), wake the neighbour.
  With one page: retake as in v0.4 (discard, open camera). `popstate` follows the same rule.

Camera from [+]
- The camera screen remembers where it came from (`start` or `captured`). Back returns there.
  The DIN frame is fitted to the visible video as today; page two is not constrained to page
  one's frame, every page gets its own capture frame.
- The stream is stopped after the shutter as today; the previous current page is parked before
  the new canvas is created, so at most one full-resolution canvas exists at any time.

Share
- `buildPdf` takes a list of `{ jpeg, width, height }` and adds one page per entry, each with
  `pageLayout` of its own size. Encoding runs sequentially: wake a parked page into a
  temporary canvas, render its frame region, encode, release, next. The current page is
  encoded from its live canvas. Peak memory is one full canvas plus one frame canvas.
- File name stays `scan-YYYYMMDD-HHMMSS.pdf`.
- Failure (encoding, PDF, share error) shows the brief warning as in v0.4 and leaves the
  document untouched.

## Data model changes

`Capture` is kept as the unit the edit views and the share code operate on (image + frame);
the app wraps the current page into a `Capture` when it opens an edit view. `Document` and
`Page` are new in `src/model.ts`. `buildPdf` becomes multi-page.

## Icons used

New: `add-page` (a page with a plus, so that it reads as "add a page"), `chevron-left`, `chevron-right`. Existing: `arrow-left`, `share`, `edit`.

## Acceptance criteria

- Scanning three pages and sharing yields a three-page PDF in capture order, each page with
  its own orientation (unit test with two portrait and one landscape frame).
- Never more than one full-resolution canvas exists (jsdom test counts live canvases across
  add, navigate, remove, share).
- Navigating between two unchanged pages ten times does not re-encode either page (test
  counts `toBlob` calls).
- Editing page 1 after page 2 was captured changes page 1 only; page 2 is bit-identical.
- Back on page 2 of 2 shows page 1 with header hidden; back again reopens the camera.
- Camera back after [+] returns to the same page that was shown before, page count unchanged.
- Share cancel keeps all pages and the current position; share success returns to the start
  page with no page left in memory.
- Twenty 12 MP pages can be captured on a mid-range Android phone and an iPhone without the
  tab reloading.
