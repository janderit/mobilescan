# v0.10 Live document detection in the camera view

## Goal

The camera view looks for the page while the user is still aiming. When a document is found
with confidence inside the dashed frame, the frame turns green and traces the paper's outline,
so the user sees before the shutter that the scan will come out right. The capture then
applies the perspective correction on its own: the captured view shows the page already
upright, without a visit to the crop/rotate view and the wand button. The detection is the
v0.8 edge search (`src/detect.ts`), always started from the static camera frame; nothing about
the maths changes, it only runs on the live video as well as on the still.

The feature is optional (a toggle next to the shutter, on by default) and it never takes the
picture by itself: the shutter stays the user's act (decision 2026-09-22, see below).

## Scope

In:
- Live detection on the camera view, throttled to a few runs per second, on a working copy
  of the video rendered like the v0.8 working image (static frame plus 5 % outward, longer
  side 800 px).
- Confidence and stability rules: all four edges found, and the corners steady over
  consecutive runs, before the outline is shown. Hysteresis against flicker.
- Overlay: the dashed frame becomes an SVG polygon. Without a document it is the static grey
  DIN rectangle of v0.1; with one it is the green quadrilateral of the detected corners,
  still dashed. A short vibration marks the moment it turns green.
- Toggle: an icon-only button with the magic-wand icon right of the shutter, `aria-pressed`,
  on by default. Off: camera view exactly as v0.9, no detection, no auto-bake. The state
  lives in the app for the session (it survives [+] and retakes) and is not persisted.
- Capture with the toggle on: the still is detected once more from the static frame with the
  same strict rule, and a hit is baked (rotation and shear, `bakeFrame`) behind the busy
  overlay before the captured view appears. A miss on the still gives the plain v0.9
  capture with the static frame; when the live outline was green at that moment the v0.4
  warning icon is shown briefly over the captured view, so the user knows why the page is not
  corrected and can retake or use the wand in the crop/rotate view.

Out: automatic capture (no shutter press), document detection anywhere in the image (the
band around the static frame is the search area, as in v0.8), detection of dark paper on a
bright desk (v0.8 limit), live tone or lighting feedback, detection on the captured view,
any zoom or exposure control of the camera, persistence of the toggle, a setting screen.

## Behaviour

Detection loop (`src/live-detect.ts`, the pure stability part in `src/detect.ts`)
1. Runs while the camera screen is shown, the stream is live and the toggle is on. It is
   driven by `requestVideoFrameCallback` where available (Safari, Chrome), otherwise by
   `requestAnimationFrame`, and skips frames so that at most one run starts every 150 ms.
   It stops with the stream (backgrounding, camera back, shutter) and when the toggle is
   switched off; switching on starts it again.
2. Each run renders the working copy with `sampleImage` from the `<video>` element (a
   `CanvasImageSource` with the stream's intrinsic size, the same size `captureStill` draws
   from) through `frameWorkingLayout(liveFrame)`, the static frame in stream pixels, and calls
   the v0.8 edge search. The 90° base is 0 and the static frame is upright, so the working
   image is the frame region plus the bands, axis-aligned.
3. Strict acceptance, unlike the wand in the editor: all four edges found (the editor keeps
   unfound edges on the frame; here a missing edge means "no document"), the frame at least
   10 % of the image width on both sides, the quadrilateral convex, and the rotation within
   the ±15° skew range (a clamped angle means the page is tilted too far; the wand in the
   editor clamps and carries the rest as corner offsets, here it is a miss). `detectFrame`
   reports the number of edges found and whether the angle was clamped so the caller can
   apply this rule.
4. Stability: a run's corners are compared with the tracked outline (the smoothed corners
   while found, else the previous hit). They agree when every corner is within 3 % of the
   frame width (in stream pixels; 1 % in the first draft, raised after the first device
   test, where hand tremor between runs kept the outline from locking). The outline is shown
   after three agreeing hits in a row and hidden after two misses in a row (a miss is a run
   without a strict hit, or a hit that does not agree with the previous one). This is
   `DetectionTracker` in `src/detect.ts`: pure, fed with results, unit tested.
5. The displayed corners are smoothed exponentially (factor 0.5 per run) so the outline does
   not jitter on a steady hand; the smoothing state resets when the outline is hidden.
6. Cost: one drawImage into a canvas of about 0.5 MP, one `getImageData`, the luminance
   conversion and four bands of gradient work. Budget 15 ms per run on a mid-range Android
   phone; at about 6 runs per second that leaves the main thread free for the video and the
   buttons. No worker, no WebGL, no persistent buffers beyond one reused working canvas.

Overlay
- `.camera-frame` becomes an `<svg>` covering the camera screen with one `<polygon>`. Its
  points are the static frame rectangle (as `layoutFrame` computes it today) or the smoothed
  detected corners mapped through the same cover transform (stream pixels to viewport). Points
  are set directly per run, no animation. The stroke is the current dashed frame colour, and
  the `found` class switches it to green (`--frame-found`, `#22c55e`) with a 150 ms colour
  transition, none under `prefers-reduced-motion`.
- The polygon never takes pointer events; the shutter, the back button and the toggle sit
  above it as before.
- On the transition to `found` the device vibrates for 15 ms (the shutter uses 30 ms), not
  under `prefers-reduced-motion` and never on the way back to grey.

Toggle
- Icon button with `magic-wand`, `aria-label` "Dokument automatisch erkennen",
  `aria-pressed` true or false. Placed on the shutter row, right of the shutter, in the dark
  style of the camera back button; the shutter stays centred. Default on. The state is a field
  of the app state, kept across camera openings and page additions until the page is reloaded.
  Not stored anywhere (no localStorage, no query string); this keeps the no-persistence rule
  of the spec untouched, and a first stored preference would be a decision of its own.
- Switching off hides the outline at once and shows the static frame; switching on restarts
  the loop from an empty tracker.
- The toggle is not disabled while the loop runs; a tap during a run takes effect before the
  next run.

Capture
1. Shutter: flash and vibration as in v0.4, the still is grabbed with `captureStill`, the
   stream stops and the loop with it.
2. Toggle on: the still is detected from the static frame scaled to the still's size (the
   `scaleFrame(liveFrame, ...)` the capture path already computes), with the strict rule of
   step 3 above but without the stability rule (one image). The live result is not used for
   the bake: the still is taken later than the last video frame, and the hand moves.
3. Hit: the page is created with the detected frame and, when `frameNeedsBake` says so,
   baked with `bakeFrame` behind the busy overlay (v0.7 warp, margins kept, target rectangle
   plus 25 % per side). A rectangle with angle 0 needs no pixel work and only sets the frame.
   Afterwards the page's frame is the upright target rectangle without offsets, exactly as
   after confirm in the crop/rotate view. Bake failure (v0.4 notice "Entzerren
   fehlgeschlagen") keeps the unbaked image with the detected frame reduced to its rectangle,
   so the user still gets a cropped page.
4. Miss: plain v0.9 capture with the static frame. If the live tracker reported `found` on the
   last run before the shutter, the warning icon is shown briefly over the captured view.
5. Toggle off: v0.9 capture, nothing else.
6. The captured view, its buttons and the edit views are unchanged: the auto-bake result can
   be cropped, rotated, sheared again and toned like any capture. Back is the retake.

Interaction with other features
- Multi-page (v0.5): [+] opens the camera with the loop running and the toggle in its current
  state; each new page gets its own detection and bake. The busy overlay of the bake shows
  before the captured view appears, so the page counter in the header updates once.
- Camera error screen (v0.4): no toggle, nothing detected.
- Zoom (v0.9): none on the camera view; unchanged.
- The wand in the crop/rotate view (v0.8) stays for pages captured with the toggle off, for
  misses and for corrections after the auto-bake.

## Data model changes

None in `src/model.ts`. `detectFrame` returns the number of edges found alongside the frame
(or a separate `detectFrameStrict` wraps it). New: `DetectionTracker` (pure) in
`src/detect.ts`, `src/live-detect.ts` for the loop over the video element, a boolean
`liveDetect` in the app state, `--frame-found` in `src/styles.css`. `captureStill` is
unchanged; the capture path in `src/app.ts` gains the detect-and-bake step behind
`runBusy`.

## Icons used

Existing: `magic-wand` for the toggle, `warning` for the miss notice. No new icons.

## Acceptance criteria

- Unit test: `DetectionTracker` reports `found` only after three agreeing hits, keeps it over a
  single miss, drops it after two misses, tolerates a corner moved 2 % of the frame width and
  treats one moved 5 % as a miss.
- Unit test: the strict rule rejects a synthetic image where one of the four edges lies
  outside the band (three edges found), and accepts the v0.8 test image with all four found.
- Unit test (jsdom, app shell): with the toggle on and a stubbed detector returning a hit for
  the still, the shutter produces a page whose frame has angle 0 and no offsets, and the bake
  ran once; with a miss, the page has the static frame and no bake ran; with the toggle off,
  the detector is never called.
- On the phone: aiming at a page on a dark desk turns the outline green within about half a
  second of holding still, the outline follows the paper edges while the phone moves slowly,
  and lifting the phone off the page returns to the grey rectangle without flicker. The
  shutter then shows the page upright in the captured view; a page photographed from an angle
  is rectified.
- On the phone: with the toggle off nothing changes against v0.9; switching it on and off
  mid-aim never leaves a stale outline.
- On the phone: a page tilted beyond the ±15° skew range never turns green (the rotation
  clamp of v0.8 would otherwise produce large corner offsets; the tracker rejects hits whose
  frame angle was clamped).
- Performance: with a counter in a dev build, runs start at most every 150 ms and each stays
  under 15 ms on a mid-range Android phone; the preview keeps its frame rate; the loop is
  idle while the app is backgrounded.
- Nothing is stored: after a reload the toggle is on again; no `localStorage` key is written
  (checked in the jsdom test).
